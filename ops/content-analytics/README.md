# Content analytics data plane

This Compose project runs Umami v3 and its PostgreSQL database separately from
`mlai-backend`. It is the raw, anonymous event data plane for pages generated by
the Content Factory. MLAI reads Umami through its private API and stores only
article/day aggregates in the application database.

The deployment deliberately has three different addresses:

| Setting | Consumer | Exact meaning |
| --- | --- | --- |
| `UMAMI_BASE_URL=http://content-analytics-umami:3000` | `mlai-backend` only | Private Umami UI/API origin on the shared Docker network. Never put this in generated code. |
| `CONTENT_ANALYTICS_TRACKER_SCRIPT_URL=https://analytics.example.com/content-signal.js` | Browser | Public URL of the generated Umami tracker JavaScript. |
| `CONTENT_ANALYTICS_HOST_URL=https://analytics.example.com` | Browser (`data-host-url`) | Public collection **origin**, with no path or trailing slash. The served tracker appends `/api/content-signal` itself. |

`collector_url` in the Content Factory contract refers to that public origin,
not to the POST endpoint. The management API, login and dashboard are not
public on `analytics.example.com`.

## Privacy and ownership invariants

- PostgreSQL is reachable only on the internal Compose network. Umami's full
  port binds to host loopback; the backend reaches it as
  `http://content-analytics-umami:3000`.
- The public TLS ingress allowlists only `GET /content-signal.js` and
  `POST|OPTIONS /api/content-signal`. Use
  [`nginx-public.example.conf`](./nginx-public.example.conf) as the baseline.
- Access logging is disabled on both public analytics routes so the reverse
  proxy does not create a second IP/User-Agent log store. Apply the same policy
  (or an explicitly IP-free, short-retention format) at any CDN or upstream
  load balancer.
- `SALT_ROTATION=day` is enforced in Compose. New page loads derive anonymous
  session IDs from a daily salt, sharply bounding ordinary cross-day linkage.
  A tab kept open across midnight can temporarily reuse its in-memory collector
  cache, so this is a privacy bound rather than a guaranteed midnight split.
- Generated pages do not call `umami.identify()`, disable automatic pageviews,
  strip arbitrary query keys and URL hashes, preserve only a bounded standard
  UTM allowlist for attribution, respect Do Not Track, and emit only the agreed
  article events. No names, email addresses, account IDs, free-form text or CTA
  form values belong in event properties.
- The tracker uses Umami's single `window.umami` global. If a customer site
  already loads a different Umami website ID, the generated collector fails
  closed to prevent cross-property events. Treat that as a rollout check and
  use a reviewed manual adapter rather than replacing the site's tracker.
- MLAI provisioning must set `replayConfig.replayEnabled` and
  `replayConfig.heatmapEnabled` to `false`, with both sample rates at zero, for
  every new **and existing** site. Pinned Umami v3.2 derives the effective
  `recorder_enabled` flag from that configuration. Verify after provisioning:

  ```sql
  SELECT website_id, domain, recorder_enabled, replay_config
  FROM website
  WHERE deleted_at IS NULL;
  ```

  Any `recorder_enabled = true` row is a release blocker. Umami has no supported
  global environment switch that substitutes for this application invariant.
- `PRIVATE_MODE=1`, telemetry and update checks are disabled. Image upgrades are
  explicit rather than initiated from the Umami process.
- Raw events have a 120-day default retention. Historical MLAI reports remain
  in daily aggregate tables; Umami's own raw dashboard will not report beyond
  the retained window.

These defaults are intentionally anonymous rather than identity analytics.
They measure whether an article attracts a visit, earns meaningful attention
and causes a CTA interaction; they do not attempt to identify the visitor.
Headline CTA milestones are exact unique-visit aggregates. Source-level CTA
joins are intentionally deferred so the daily worker stays bounded as article
counts grow; the dashboard does not present unavailable attribution as zero.

## First deployment

1. Copy `.env.example` to `.env`. Generate the database password and
   `UMAMI_APP_SECRET` independently with `openssl rand -hex 32`. The database
   password must remain URL-safe because it is interpolated into
   `DATABASE_URL`.
2. Keep both required image values as immutable `tag@sha256` references. Before
   changing them, resolve the digest from the official registry and test the
   update in staging. Compose intentionally has no `latest` fallback.
3. Create the shared network once:

   ```sh
   docker network create mlai-shared
   ```

   For `docker-compose.local.yml`, use the existing local network instead:
   set `MLAI_SHARED_NETWORK=mlai-local-shared` in this stack's `.env` (and
   create that network if the local backend bootstrap has not already done so).

4. Validate and start the database plus daily backup first:

   ```sh
   docker compose config --quiet
   docker compose pull
   docker compose up -d database backup
   docker compose ps
   ```

5. Start Umami. Its image runs pending Prisma migrations during startup; do not
   set `SKIP_DB_CHECK` or `SKIP_DB_MIGRATION`:

   ```sh
   docker compose up -d umami
   docker compose logs --tail=200 umami
   docker compose ps
   ```

6. Reach the admin UI through an SSH tunnel to the loopback bind (or through a
   separate VPN/identity-aware private ingress), change the bootstrap password
   immediately, then create a dedicated MLAI service user that can provision
   sites and read reports. Store its credentials only in the backend secret
   store. Umami v3.2 does not expose separately scoped API keys: `UMAMI_API_TOKEN`
   accepts that user's normal login bearer, while username/password lets the
   backend obtain and refresh the bearer reproducibly.
7. Configure the backend environment using the contract below, run Django
   migrations, and start its dedicated `analytics-sync` service.
8. Install a public TLS ingress containing only the two exact routes. If using a
   CDN, prevent direct origin access, overwrite rather than trust the configured
   client-IP header, do not cache the collector route, and do not expose a broad
   `/api/` prefix.
9. Run the TLS/CORS/private-route/CSP gates in “Smoke tests” before enabling an
   organization.
10. Start retention only after a valid backup exists:

   ```sh
   docker compose up -d retention
   docker compose ps
   ```

## Backend environment contract

Add these to the production `mlai-backend` secret/environment configuration:

```dotenv
# Private Docker address. Never emit this value to customer sites.
UMAMI_BASE_URL=http://content-analytics-umami:3000

# Umami v3.2 has normal login bearers rather than separately scoped API keys.
# Prefer a dedicated service user's username/password; API_TOKEN may hold its
# current login bearer when credential injection requires token-only auth.
UMAMI_API_TOKEN=
UMAMI_USERNAME=
UMAMI_PASSWORD=
UMAMI_TEAM_ID=

# Public browser-safe values. HOST_URL is an origin, not the POST endpoint.
CONTENT_ANALYTICS_TRACKER_SCRIPT_URL=https://analytics.example.com/content-signal.js
CONTENT_ANALYTICS_HOST_URL=https://analytics.example.com
CONTENT_ANALYTICS_FIRST_PARTY_PROXY_ENABLED=false

CONTENT_ANALYTICS_SYNC_ENABLED=true
# Completed days become due once per day. The worker may poll hourly so bounded
# initial GSC backfill chunks can make progress without re-fetching steady sites.
CONTENT_ANALYTICS_SYNC_INTERVAL_SECONDS=86400
CONTENT_ANALYTICS_SYNC_POLL_SECONDS=3600
CONTENT_ANALYTICS_SYNC_BATCH_LIMIT=10
CONTENT_ANALYTICS_SYNC_LOOKBACK_DAYS=3
CONTENT_ANALYTICS_SYNC_MAX_BACKFILL_DAYS_PER_RUN=30
# Top UTM sources enriched with exact visit counts per article/day. Overall CTA
# milestones remain exact; source-level CTA attribution is intentionally deferred.
CONTENT_ANALYTICS_UMAMI_SOURCE_ATTRIBUTION_LIMIT=3
CONTENT_ANALYTICS_GSC_FINALIZATION_LAG_DAYS=3
CONTENT_ANALYTICS_GSC_INITIAL_BACKFILL_DAYS=480
CONTENT_ANALYTICS_GSC_QUERY_LIMIT=100

# Search Console: prefer a mounted secret file; the single-line JSON setting is
# available where the deployment platform cannot mount one.
GOOGLE_SEARCH_CONSOLE_SERVICE_ACCOUNT_FILE=
GOOGLE_SEARCH_CONSOLE_SERVICE_ACCOUNT_JSON=
```

The service account must be added to each exact Search Console property. Do not
grant it broader Google Cloud roles than required for the Search Console API.
The content-analytics implementation does not scrape Google or Bing dashboards.

The initial connector stores the documented Search Analytics API's web clicks,
impressions, CTR, position and best-effort query rows. Google's separate
generative-AI performance view is still a staged Search Console rollout and is
not exposed as a distinct documented Search Analytics API request at the time
of this implementation. Do not infer AI-feature impressions from ordinary web
impressions. `ArticleSearchDaily.surface` is intentionally retained as the
extension point for that feed when Google publishes a stable API contract.

## Public and private ingress

The public hostname should behave like this:

```text
GET  /content-signal.js       -> Umami tracker (cacheable)
POST /api/content-signal      -> Umami collector (never cache)
OPTIONS /api/content-signal   -> Umami CORS preflight
anything else                 -> 404/403
```

Keep the admin UI and authenticated API on one of:

- the Docker network only (the normal backend path);
- an SSH tunnel to `127.0.0.1:3000`; or
- a separate private hostname behind VPN and identity-aware access.

Do not protect the two browser routes with login middleware. Do not expose the
private hostname or an Umami share URL to customers; the product UI reads MLAI's
aggregate API instead.

Customer-site CSP must explicitly allow the public origin:

```text
script-src 'self' https://analytics.example.com;
connect-src 'self' https://analytics.example.com;
```

Preserve any existing directives. Prefer a response header over a meta CSP, and
do not broaden either directive to `https:` or `*` just for analytics.

## Smoke tests

The script verifies certificate/TLS policy, the tracker-embedded collection
path, cross-origin preflight, denial of UI/API routes, and optionally a deployed
article's CSP:

```sh
chmod +x ./smoke-test.sh
PUBLIC_ANALYTICS_ORIGIN=https://analytics.example.com \
ARTICLE_ORIGIN=https://customer.example.com \
ARTICLE_URL=https://customer.example.com/articles/example \
./smoke-test.sh
```

`ARTICLE_URL` is optional for local iteration but mandatory as a production
release gate. For loopback-only testing, set `ALLOW_HTTP_LOCALHOST=1` explicitly.
Also open a generated article with browser Do Not Track enabled and confirm that
no collector request is made.

## Daily backups and restore drills

`backup` immediately writes a compressed, custom-format dump and repeats every
24 hours. Incomplete dumps retain a `.partial` suffix and never satisfy the
retention precondition. Successful dumps are kept for 30 days by default.

The Docker volume is not an off-machine backup. Replicate it to encrypted,
access-controlled object storage and alert when `backup` is unhealthy. At least
quarterly, restore into an isolated stack and compare website/event counts.

List and validate a dump:

```sh
docker compose run --rm --entrypoint sh backup -c \
  'ls -lh /backups/umami-*.dump && pg_restore --list "$$(ls -1t /backups/umami-*.dump | head -1)" >/dev/null'
```

The following procedure **destroys the current Umami database**. Prefer an
isolated restore-drill project; in an actual incident, verify the selected dump
and stop writers first:

```sh
docker compose stop umami retention backup
docker compose exec database sh -ec \
  'dropdb --force -U "$POSTGRES_USER" "$POSTGRES_DB"; createdb -U "$POSTGRES_USER" -O "$POSTGRES_USER" "$POSTGRES_DB"'
docker compose exec -T database sh -ec \
  'pg_restore --exit-on-error --no-owner --no-acl -U "$POSTGRES_USER" -d "$POSTGRES_DB"' \
  < /secure/path/umami-YYYYMMDDTHHMMSSZ.dump
docker compose up -d umami backup retention
docker compose logs --tail=200 umami
```

After restore, rerun the smoke tests and a forced backend sync for one known
organization before declaring recovery complete.

## Raw-event retention

`retention` runs [`prune-raw-data.sql`](./prune-raw-data.sql) once per day. It:

1. refuses to run without a completed dump from the last 48 hours;
2. requires a retention value between 30 and 3650 days;
3. takes a transaction-scoped advisory lock;
4. validates the pinned Umami v3.2 tables and columns it will touch (including
   recorder and heatmap rows);
5. deletes child/event/session raw rows in dependency order in one transaction;
6. keeps an old session if any known v3 row still references it; and
7. updates table statistics after a successful prune.

If a future Umami release renames a required table or column, the job fails
closed instead of guessing. Review the upstream Prisma schema and update the SQL
in staging before re-enabling retention. Monitor table bloat and autovacuum;
large first-time purges may need a controlled maintenance window.

## Image and schema upgrades

Never change an image digest as part of an unattended update. For each upgrade:

1. read the Umami release notes and Prisma migration notes;
2. take and validate a fresh pre-upgrade dump;
3. test the exact new digest, API provisioning, aggregate sync, retention SQL and
   restore in staging;
4. stop `retention`, update `UMAMI_IMAGE`, pull, and start only `umami`;
5. inspect migration logs and run `ANALYZE` after a major upgrade;
6. run smoke tests and a known-site sync; then restart `retention`.

Schema migrations may not be reversible. A rollback therefore means restoring
the pre-upgrade dump with the previous pinned image, not merely changing the
image tag.

# E5: initial CMS onboarding into one original goal — 17 October 2026

The current native path begins after CMS connection. Its owner must still
connect a key, then press Set up articles. The remaining onboarding work combines
the exact credential destination, review preference, existing author/category
consent and first-article price in one owner acceptance. Closing the page must
not discard verification or require another start button.

The first implementation supplies a closed, read-only initial offer. It binds
the actual founder/company/config, current explicit CMS channel selection and
revision, canonical public/API destinations and an actual integer price. It
expires after 15 minutes. Unknown prices do not become free. No credential,
provider observation, connection, reservation, payment or work permission is
created by an offer; its digest is only display identity. The initial-only
reader refuses an existing connection, including a disconnected original paid
site. Such rebinding requires its separate explicit transfer design.

Future acceptance must validate the displayed offer's original expiry, then
compare its actual scope, destination and price with a fresh server read.
Refresh timestamps/digests naturally differ; matching a newly generated digest
is not the consent check. A rechecksummed caller price never overrides the
actual current price at the first reservation.

The next runtime boundary will accept the offer and all answers under the
owning organization lock. It must allocate the real original operation,
connection and private key identities server-side, encrypt the proposal before
HTTP and reserve the accepted first-article amount once before verification.
Use the existing native financial subject and immutable setup intent so the
same operation/hold/price/acceptance time and budget become ordinary `cms-setup`
and then `cms-goal`; no successor price or additional debit is permitted.

Before identity verification, the allocated connection must grant no current
CMS/Git capability. A distinct server-only connecting lease must recheck the
actual founder/company/channel/config, original unrefunded hold, private pending
key, original intent and budget before/after each fixed GET. The public site is
read without a key first. Only actual publishing identity may atomically
complete the original private key and admit normal setup discovery. Losing a
reply must reuse the exact original committed result. No model/provider-write
operation may use a provisional connection or an offer.

Bad initial credentials require only fresh key input for this original setup,
without changing consent, budget or hold. Original owner scope must fence a new
credential nonce and any late worker. Pending ciphertext has a 24-hour erasure
deadline, independent of rollout; cancellation/offboarding/purge must queue
original unused settlement before erasing financial proof. Existing setup
settlement can be reused only after its historical original intent verifies.
Generic Git reconciliation and operation-detail surfaces must exclude the
private connecting job. A rollout pause must retain pending encrypted input.

Chat must show the actual initial offer and explicit destination together, keep
credentials only in dialog/transport memory, persist only a scoped UUID, and
recover unknown acceptance through reads. A complete browser/ORM test must run
one acceptance into the same existing setup/controller/publication chain, with
injected verification/worker/reply loss and one original spend/post.

`ARTICLES_CMS_ONBOARDING_ENABLED=false` is independent and remains off. Only the
offer contract/reader is implemented in this slice; no initial owner route,
credential queue, provisional capability, payment, controller or Chat form is
enabled by it. Runtime acceptance, lifecycle/settlement, status and UI are next.

The follow-on private planner now carries the server-allocated connection,
original root and key identities into the existing closed native setup intent.
It preserves the accepted review/cost choices, original acceptance time and
stable native financial subject without fabricating an author, policy, hold,
lease or milestone. Historical validation uses the offer at actual acceptance;
it cannot refresh that time or the original 24-hour proposal deadline. A future
worker still needs separate current ownership, private lease, pending key,
original hold and budget checks. The initial offer also refuses legacy Git
repositories whose configuration has no connection row; that is transfer work.

Seven follow-on cases cover stable identity/time, review/free consent, expired
offers, wrong scope/owner, resource aliases, coerced choices and the legacy Git
boundary. All 1,451 website no-database tests pass; current worker, owner route,
cancel/expiry settlement and combined Chat onboarding are still unimplemented.

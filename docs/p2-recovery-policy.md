# Founder recovery policy

All behavior defaults off. The existing scheduled self-heal sweep and website prepare controller share registry decisions; no additional supervisor or database model is introduced. Legacy organizations keep the existing recovery path and receive read-only observations. `manage.py self_heal_report --json [--org ID]` performs no writes. The optional weekly report writes only private `pillar_strategy.self_heal.dry_run` metadata.

Run decisions reserve attempts under organization/config/run locks, and remote actions execute after commit. Evidence-only run receipts use queryset updates so they preserve `updated_at`. Transient backoff is 1, 2, 5, 10, 20, 40 and 60 minutes, then 60; repair attempts stop at 6, source re-pins at 2, strategy attempts at 2 per rung/source and 6 per organization UTC day, and every item has a 48 hour wall. Current-item delivery stops recovery; historical delivery on the original charge independently prevents inappropriate refunds.

Each reserved remote action retains a `self_heal_v1.pending_action` receipt with action, attempt, state and a two-minute lease. A lost response or worker death retransmits the same attempt rather than consuming another failure attempt. This is an additive durable receipt refinement. The CF resume action retains its existing operation-attempt authority. A revoked cohort or executor flag prevents dispatch on the final check. Automated repository actions first reserve a daily PR slot; actual PR URLs reconcile reservations during ingest. Founder clicks remain allowed and are counted.

Website goal recovery runs within the existing prepare lease. It does not update the operation before the controller's original compare-and-set. Replayed failure occurrence IDs cannot advance the goal twice. Source changes and cancellation still use the existing connection authority guard. A fresh hosted rung is chosen only when the hosted service proves readiness; otherwise native progression continues. Exhausted channels save a copy-ready intent and one source-scoped ticket without asking founders to choose a channel.

Channel fallback preserves the original run request, website tuple and billing. An additive authenticated CF resume control converts only remaining delivery steps to content_only. Enable the new default-off CF `CONTENT_FACTORY_SELF_HEAL_ENABLED` executor before backend `ARTICLES_CHANNEL_SWITCH_ENABLED`, and enable policy last. Pending intents are retained until the executor acknowledges them; a channel receipt alone never proves an article was delivered.

Integration extensions: `registry_policy.organization_read_scope` reuses a joined config only for one decision, without changing global cohort reads or mutation authority. The existing PostgreSQL CI lane now selects the new P2 test modules; the test assignment guard rejects new omissions. A 500 organization observe-only decision batch has at most 3 queries and passes the 2 second local gate; this is a local selection/decision measurement, not provider execution latency.

Validation checkpoint: 257 PostgreSQL P2 tests, 143 broader policy/goal/cohort/reconciliation regressions, 17 focused policy tests. Independent review, the final real hosted/channel composition, full production stop-code replay and deployment acceptance remain open until the final integration checkpoint. No production changes were performed.

## Background work and stop codes (Phase 0, A2, A3, A16)

Background work is decided by who asked for it, not by workflow name. `founder_journey_alerts.is_scheduler_run` is true only for a run whose saved `run_request.request_source` is `mlai_backend_scheduler`, or for an old `island_refresh` row saved before the scheduler stamped `request_source` (unless its client request id starts with `island-research:`). `founder_run_q()` is the SQL form. Every alert path uses it: `queue_founder_journey_alert` and the batch variant write no receipt for a scheduler run, and the founder-journey, staff-rule and stuck sweeps select founder runs with `founder_run_q()`. Founder-paid island research (workflow `island_refresh`, a founder request source) therefore alerts like any other founder run. The self-heal sweep never selects scheduler runs. `advance_rung` and `switch_channel` apply only to article, `article_system_setup` and `repo_scan` runs and to website prepare operations; any other run stops instead. `channel_switch.switch_to_copy_ready` refuses other workflows before calling CF.

A run alert leads with the code that blocks the run (`run_blocking_code`) when the run is blocked, failed or denied, or when its failure asks the founder to act. With several codes, connection or authority codes come first, then website setup, delivery, and quality or safety holds; self-heal recodes come last.

Two operator commands default to a dry-run report. Run each with `--apply` only after the dry-run report is reviewed and the owner has signed off on that write.

- `manage.py quiesce_self_heal_history [--apply] [--before YYYY-MM-DD] [--org ID] [--limit N] [--json]` stamps scheduler runs and untouched founder failures created before the horizon (default `ARTICLES_FOUNDER_JOURNEY_ALERTS_SINCE`) with `self_heal_v1.last_action = "none"`. On scheduler runs it restores the `error_code` the engine overwrote with `SELF_HEAL_*`, keeping the engine's stop under `self_heal_v1.stop`. It counts pending alert receipts for scheduler runs and does not change them. Writes use the run row lock and a queryset update, so `updated_at` does not move. A second run changes nothing.
- `manage.py replay_stopped --code CODE [--since ISO] [--apply] [--org ID] [--limit N] [--json]` re-opens website prepare operations stopped on `CODE` through the owner's Try again (`start_prepare(..., retry=True)`), as the founder who authorised the website and with the operation's own goal target, so a first-article goal is retried rather than superseded. It selects only the newest operation of a connected, selected website's current generation. It skips an operation at its setup dispatch cap, a startup with no automatic pull request slot left today, an event-owned child and a finished first-article goal. It records `replay_v1` on the receipt, so the same code and `--since` never replay an operation twice.

## Replay corpus of founder failures (F5, level 1)

Every pull request replays the catalogue's founder failures through the function that decided them. Content Factory keeps its records and runner in `backend/evals/replay` (`tests/test_replay_corpus.py`); the backend keeps the alert, journey and system-stopped-run cases in `content_factory/fixtures/replay` (`content_factory.tests_replay_corpus`). A record (`replay-record-v1`) holds the workflow, step, stored code, framework fingerprint, public HTTP responses and other inputs without secrets or personal data, and the expected outcome: `pass`, `ask:<action>` or `code:<CODE>`. Seed records are synthetic, shaped from the catalogue.

`manage.py export_replay_record --run-pk PK [--output FILE]` is read-only (PostgreSQL `SET TRANSACTION READ ONLY`, and the transaction is rolled back on any engine). It writes a draft record built from an allowlist of code-shaped fields, booleans and small integers; free text, tokens, e-mail addresses, names, the founder's domain and repository and any repository content are never copied, and the command fails closed if a forbidden shape or the founder's domain or repository still appears. Outside local and test environments it needs `--allow-production-read` and an owner go-ahead. A reviewer checks the redaction and sets `redaction_reviewed_by`, the handler and the expected outcome before the record is committed (D11).

**Rule: a pull request that says it fixes a founder issue adds or updates a replay record** for that failure. CI does not enforce this yet. After release, `replay_stopped` carries the fix to founders already stuck.

## Staff operation actions and the escalation ladder (Phase 4, F10)

Behind `MY_STARTUP_STAFF_CONSOLE_ENABLED` (unchanged, default off), the staff console's action endpoint (`POST /community-chat/admin/startups/<org>/actions/`) also takes `operationId` for the startup's current website preparation (`content_factory/staff_operation_actions.py`):

- `restart_prepare`: the founder's own Try again under the founder who authorised the website. With `resetAttemptCap: true` it also clears the setup dispatch cap and the scan budget hold; that reset has its own cap (`CAP_RESET_LIMIT`, 1 per preparation) and is recorded in `staff_cap_resets_v1`.
- `rescan`: "Check website again" from the server on a stopped or finished preparation; the scan budget holds.
- `reset_setup`: Try again, then start the setup over from a fresh scan; the setup dispatch cap holds.
- `replay_current_build`: the `replay_stopped` replay of this one preparation, keyed `CODE@build:APP_RELEASE`, so a stop is replayed once per build.

Every action needs a note (why) and an `idempotencyKey`; a repeat with the same key replays the first answer. Each call, refused or done, appends a `staff_actions_v1` row to the operation's receipt (who, when, why, state before and after). A staff action never approves or merges a setup pull request: those requests are refused (`founder_consent_required`) and audited, and a preparation resting on a founder ask is refused (`founder_turn`). Choosing the articles page for the founder, regranting a free article and archiving a duplicate are not offered. The startup detail lists only the actions the server offers (`website.operation.actions`).

Each staff console row carries `escalation`, the plan 7.6 ladder as data (`content_factory/staff_escalation.py`): a generic or internal stop reaches staff at once, a failed run at 2 hours, an unanswered ask follows E7's reminders and staff threshold, and anything still waiting on us after 48 hours sends one owner escalation through the stuck-alert sweep (same channel and `ARTICLES_FOUNDER_STUCK_ALERTS_ENABLED` kill switch; only for stops that crossed 48 hours within the last 7 days). `staff_fixing` shows B25's bounds.

The two new alert rules ship in shadow (plan 7.5 rule 7) behind `ARTICLES_STAFF_ESCALATION_LADDER_ENABLED` (default off). Off, the sweep keeps the six-hour failed-run wait and only counts the owner escalations it would queue (`owner_escalations_shadow` in the sweep result and a `founder_stuck_owner_escalation_shadow` log line); the console ladder shows the six-hour wait and marks the owner rung `shadow_not_sent`. On, a failed run alerts after two hours (`founder_stuck_alerts.RUN_STUCK_AFTER`) and the owner escalation is queued.

A restart on the goal runner opens a successor preparation (a stopped goal is terminal); the action counts that as re-opened, as `replay_stopped` does, and writes the audit row on both operations.

## Class before wall, original codes and one alert per cause (Phase 1, B1, B2, B5, B6)

`is_scheduler_run` is the one audience test for the engine and every alert producer. Besides the saved request source it now also treats a run whose admission receipt names a scheduler principal (`run_owner_v1.identity.principal.kind == "scheduler"`) as background work; `founder_run_q()` matches it in SQL. The staff provider-error-rate rule uses `founder_run_q()` instead of a workflow-name exclude. Self-heal candidates stop at the alerts' history horizon (`ARTICLES_FOUNDER_JOURNEY_ALERTS_SINCE`); an invalid horizon selects no runs. The wall counts from the run's own failure (its latest failed or blocked step's end, else its last update), not from the first sweep.

`ARTICLES_SELF_HEAL_CLASS_BEFORE_WALL_ENABLED` (default on) reads the failure class before the 48-hour wall. A `needs_user` item returns `await_owner` with no wall and is looked at again once a day; a parked website operation in `needs_user` is left alone until its state changes. Unsupported and unregistered codes stop at once without a cap. An action the engine already has in flight (reserved or uncertain) settles first, before the class is read. Retried and repaired items still stop at the wall. The refund sweep keeps its own 48-hour clock from the run's creation, so an awaited founder ask is still refunded at 48 hours. A run whose points were refunded or whose free article was released is then terminal (owner decision D16): self-heal records `none`, a founder `resume` is refused with `409 run_refunded_start_again`, and the founder's line is `stopped` with "Try another topic" (start again).

`ARTICLES_SELF_HEAL_PRESERVE_CODE_ENABLED` (default on) never overwrites `error_code` on a capped stop. The stop is recorded as `self_heal_v1.stop = {code, cap, at}` and the `self_heal_capped` alert carries `original_code`, `failure_class`, `cap` and `stop_code`. The stuck-founder sweep skips a run with a recorded stop, because `self_heal_capped` already alerted for it.

`run_terminal` and `self_heal_capped` use one alert slot per organisation, workflow and original code (`run_incident_slot`), so repeated failures with one cause raise one alert; a run without a code keeps its own alert. Nightly scheduler runs alert only through `background_job_digest`, run as its own self-heal sweep (`background_job_digest`, on with `ARTICLES_STAFF_ALERT_RULES_ENABLED`): `background_job_failing` when one startup's nightly job of a workflow failed three Melbourne nights running (one alert per streak, also once the streak is older than the 8-night lookback), and the global `background_job_failure_spike` when at least 5% of the startups that ran a nightly job, and at least three, failed on one night. A night counts as failed for a startup only when none of its nightly runs completed that night.

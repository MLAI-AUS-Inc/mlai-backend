# Roo avatar fur migration proposal — 18 November 2026

Status: proposed. The migration file is committed for review. Applying it to
any shared or production database still needs the owner's explicit approval
of this exact migration, and the deploy gate needs the matching plan hash
(see [Deployment gate](#deployment-gate)).

## Exact proposed migration

`community_chat/migrations/0019_roo_avatar_fur.py`, depending on
`community_chat.0018_chat_intro_welcome`. It was generated by
`makemigrations` and has two operations on `CommunityRooAvatar`
(table `community_chat_communityrooavatar`):

1. `AddField` `fur`: nullable/blank varchar(32) with five fixed choices:
   `golden_sand` → Golden sand; `blue_flier` → Blue flier;
   `ironbark` → Ironbark; `snow_gum` → Snow gum;
   `midnight_wallaroo` → Midnight wallaroo.
2. `AlterField` `hair`: the same nullable/blank varchar(32) with the same five
   stable IDs. Only the frozen display labels change: `honey_tuft` → Tuft;
   `cocoa_curls` → Curls; `peach_fringe` → Swept fringe; `lilac_bob` → Bob;
   `mint_mohawk` → Mohawk.

On PostgreSQL, `sqlmigrate community_chat 0019` produces one statement:

```sql
ALTER TABLE "community_chat_communityrooavatar" ADD COLUMN "fur" varchar(32) NULL;
```

The `hair` change is a no-op in SQL, because choices are not stored in the
database. The migration is additive: a nullable column with no default, no
backfill, no data rewrite, no new index or constraint, and no change to any
other table. Existing rows read null fur, which is the default "Outback red".
Saved hair IDs are untouched.

The file's SHA-256 is
`2d0e50b7f181af55b8d67febacd486c2e579d01458ae035fc6ef718c06b0160e`.

## Compatibility

- The previous release ignores the new nullable column, so the schema can be
  applied before the new code serves.
- The new code reads and writes `fur`, so it must not serve before the column
  exists. The deploy applies migrations before switching the runtime.
- Clients released before the fur slot send four outfit slots. The API keeps
  accepting that and leaves the saved fur unchanged; see the
  [account contract](community-chat-roo-avatar.md#update).
- Reversing the migration drops the `fur` column and so loses saved fur
  choices. Hair, glasses, jacket and shoes are unaffected.

## Deployment gate

`deploy.sh` refuses to apply pending migrations unless the repository variable
`APPROVED_MIGRATION_PLAN_SHA256` equals the SHA-256 of the canonical
`migrate --plan` output. When this is the only pending migration, the plan is:

```text
Planned operations:
community_chat.0019_roo_avatar_fur
    Add field fur to communityrooavatar
    Alter field hair on communityrooavatar
```

and its hash is
`a87769b28f2ad95ccf029d306f611a85466c455c64dfd52ee8929c6b36655d70`.

That hash holds only if nothing else is pending in production. If another
migration is still pending at deploy time, the plan and hash differ: use the
plan the deploy prints, and approve that exact plan instead.

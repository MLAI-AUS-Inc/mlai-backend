# B5: durable setup delivery and reconciliation

14 October 2026.

**Status:** proposal for owner approval; documentation only. No implementation, migration, database-backed validation, rollout or production repair is authorized by this note. Preparing or merging this documentation does not approve implementation.

**Source baseline:** backend `7caa968c91802a1d557ee065f40e772566aa818c`; Content Factory (CF) `a96a362a0c653eaddce6f36111e0d2a701eeef64`. The 13 October v3 runbook's B5 is the requirement. Phase A backend PR #1010 and CF PR #980 are dependencies, not assumed changes in these baselines. B1's separately reviewed failure contract is the classification interface.

The owner should see the saved setup outcome even if a worker restarts or a response is lost. A delivery problem must not restart setup, consume another article charge, replace a causal setup failure, or ask the owner to repair service credentials. The backend may recover current state and verified milestones from a trusted snapshot; it may not invent approval or replay publication, refunds or messages while doing so.

B5 therefore extends existing machinery. Its missing pieces are durable PUT obligations, immutable digest/scope validation, precise delivery dispositions, longer recoverable retries, schema validation before any write, and a state-only reconciliation path.

## Scope and contract

Initial strict v1 coverage is the website-setup lifecycle: `article_system_setup` callbacks and snapshots, plus `repo_scan` snapshots linked to an originally authorized website-prepare dispatch. Unrelated article generation, `article_complete`, topic selection and notification callbacks retain the existing compatibility path. A callback carrying a whole article may be legitimate; no new small blanket callback limit applies to it. Extending strict coverage to first-article delivery is a separately reviewed contract change. This setup-first slice is a **proposed sequencing decision/deviation** from the runbook's every-callback/full one-shot target, not a reduced definition or completion of B5. Ultimately every relevant one-shot event type, including article generation/publication outcomes, needs validated durable delivery. Existing unrelated callbacks retain current behavior until their producer inventory and adapters are approved; the initial slice cannot claim universal delivery, the nightly goal, or one-shot certification.

Define a byte-identical schema in both repos' `contracts/` for setup callbacks, snapshots and acknowledgments. Keep `contracts/run-statuses.json` as the existing status vocabulary; delivery disposition is a separate axis, not a new run status. Use the backend's existing DRF validation infrastructure with explicit schema-conformance tests. Choosing a new schema-validator dependency requires a pinned dependency/lock change in the implementation PR; this design does not assume one is installed.

A v1 transport record has immutable `delivery` metadata and a typed `body`. A thin endpoint adapter validates it before producing the existing flat handler input:

- `schema_version=1`, `kind=setup_callback|run_snapshot`, `event_id`, registered `event_type` for callbacks, `run_id`, `workflow`, `emitted_at`, `payload_sha256` for the full immutable envelope and `state_sha256` for its canonical shared-state projection;
- original authority scope: organization/proven dispatch reference, domain, repository ID/name, app root, branch, website connection ID and **connection_generation**, original operation ID/attempt and deletion epoch;
- run execution order: **generation** and **state_version**, both nonnegative integers. These are different from connection generation and operation attempt. Reject booleans, missing halves, conflicting aliases and coerced numeric strings in v1;
- exact source/branch/preview/proof identifiers appropriate to the event. A digest checks immutable bytes; it does not prove a build, grant permission or constitute owner approval.

Validate IDs rather than truncate: `event_id` and backend `run_id` must be safe ASCII identifiers of 1–100 characters, with no path separators; operation/connection IDs must be UUIDs. Registered event types are bounded by the ledger's 100-character field. The HTTP path run ID, envelope run ID and canonical run-ID aliases in the body/run request must agree. Parent/source/child provenance IDs remain distinct and must instead match their separately saved relationship. Inventory `job_id` at every enrolled producer: if it aliases the run, require equality; if it denotes a separately bound Celery task, validate that exact persisted task/run binding. A differing parent ID or legitimate task ID must not be rejected merely because its text differs from `run_id`. Reject unsupported versions/types with a typed 422, not a successful unknown-event acknowledgment.

Proposed v1 setup limit: 2 MiB of decoded JSON, depth at most 16, diagnostics at most 64 KiB, bounded path/string/list fields declared per event. Large logs, code, HTML and screenshot data stay in artifacts, with bounded digest/reference fields in the envelope. The implementation must inventory actual setup producers and fixtures before fixing individual list limits. Legacy unrelated callbacks keep their current request limits.

`repair_status` needs a compatibility adapter, not a blanket string restriction. CF `_finalize_setup_failure` legitimately places a structured build-repair report at diagnostics `repair_status`; other producers use a status string. Preserve the object as bounded `repair_diagnostics` and use a validated `repair_state` string only when an actual status exists. Record original-body digest before adapting. Never stringify a dict into an actionable status or reject all current dictionary diagnostics as malformed. Keep legacy string/status aliases only in the explicit v0 adapter.

Canonical digest: UTF-8 JSON with sorted keys, fixed separators and non-finite numbers rejected. `payload_sha256` covers the complete immutable `{schema_version, kind, event_id, event_type, run_id, workflow, emitted_at, scope, execution, state_sha256, body}` object, excluding only its own digest and mutable delivery retry/lease metadata. It therefore binds kind/run/original authority identity as well as body bytes; changing scope with the same body cannot reuse the original digest. The complete transported body also excludes the local delivery journal, leases, acknowledgment metadata and transport receipts: STATUS references to the envelope digest must not be serialized back into that envelope or its shared-state projection. This avoids a digest self-reference and prevents acknowledgments from causing mirror/ack feedback loops.

Every v1 callback/snapshot also carries `body.state_projection`, built from the same committed STATUS record: canonical run/approval status, current step, run execution generation/version, the unchanged B1 causal failure/occurrence provenance, and the contract's allowlisted exact proof records/references (source/branch/preview/artifact identities and gate receipts). Exclude transport IDs/times, formatter aliases, notification prose, the local delivery-intent journal, leases, acknowledgment metadata, transport receipts and fetched preview data. The optional RunRecord journal is local storage metadata, never mirrored business state or proof. `state_sha256` hashes this canonical projection together with the original scope. The projection fields/optional-field normalization are versioned in the shared schema; the producer persists them at commit, and the receiver recomputes both digests before comparing or applying. Equal-version callback and snapshot can have different full payload hashes but must have the same shared-state hash. A partial callback cannot invent a hash for omitted proof: it must carry the committed projection or remain outside v1.

Normalization is versioned and deterministic. Retry the same bytes and event ID. A new corrected body is a new event with `supersedes_event_id`, not an overwrite of a previously accepted ID. Acknowledgments echo and validate `schema_version`, `kind`, `run_id`, `event_id`, `payload_sha256` and `state_sha256`; the full payload hash binds the original scope identity without exposing that entire scope in an acknowledgment.

## No-migration storage and producer commit

A safe no-database-migration approach is feasible for the configured single-host persistent volume: extend the callback filesystem outbox with a snapshot queue sharing its atomic writer, lifecycle fence and delivery state machine. Keep callback POST and mirror PUT as distinct kinds/targets. Do not store service authorization headers, GitHub credentials or arbitrary RUN_REQUEST data in envelopes. Select original scope/proof-relevant fields explicitly; reject secret-bearing v1 bodies. Protect artifact references and capability URLs under the same access/retention rules as the underlying run, and redact them from logs.

The existing callback outbox guarantees write-before-send once its sender is called. It does not make a preceding STATUS write and a later callback invocation atomic. For material setup transitions, add an optional, bounded delivery-intent reference journal to the CF `RunRecord` schema. This is a file/model change, not a database migration:

1. Under lifecycle then run locking, validate the original attempt and construct immutable snapshot/callback bytes for the next state version. Persist the envelope files atomically in prepared state; abort the transition if persistence fails.
2. Atomically replace STATUS with the new business state and the intent references/digests in the **same JSON commit**. Every store write/merge must preserve the journal; adding an unknown JSON property that later model serialization discards is not sufficient.
3. Release producer locks, then let the common delivery loop send only references present in a committed journal. A crash before STATUS commit leaves an uncommitted prepared file, which cannot advertise the proposed transition. A crash after commit leaves a discoverable, durable obligation.
4. Write acknowledgment metadata separately, atomically. Transport acknowledgments do not increment business `state_version` or generate another mirror update. Prune acknowledged journal references on a later business commit or run-retention pass, only with a durable matching acknowledgment.

For progress, coalesce only unsent snapshots within the same run execution/scope; keep the newest committed state version. Never overwrite an in-flight record or a terminal/owner-action callback. A superseded progress snapshot has a durable link to its replacement. Terminal and awaiting outcomes persist before their immediate attempt; task-postrun/finalize flushes are accelerators, not the durability mechanism. Startup/sweeper discovery scans committed journal references as well as pending files. Missing/corrupt intent bytes are an integrity error, not permission to reconstruct a side-effect callback from a human-readable message.

The journals and all pending files obey `operation_fence` deletion/cancellation watermarks. Purge retires content-bearing entries only under the existing lifecycle lock and leaves identifier/digest-only fencing receipts. An acknowledgment cannot resurrect deleted data. Disk-full/write/fsync failure is surfaced before a success state is advertised; it cannot silently fall back to an in-memory queue.

**Boundary:** this design survives process/container restart on the same validated persistent volume. It does not promise survival of droplet/disk loss. Multi-host senders without one filesystem with proven locking, or a requirement for disk-loss delivery, needs an approved durable storage/backup decision. If the deployment cannot establish that boundary, enabling B5 is blocked; a new database-backed CF outbox would need its own migration approval.

## Concurrent delivery and retries

Reuse the existing sweep entry point. Under a short filesystem claim lock, atomically set each due record's lease nonce, owner, expiry and attempt count. Release locks before HTTP. Proposed claim TTL is 120 seconds with a 30-second send timeout; assert configured TTL exceeds the complete bounded send budget. Only the same nonce may settle the result. After expiry another process may claim; a late original sender must not overwrite its replacement's receipt. Kernel locks and persisted leases work across processes sharing the volume; no process-local timer or Redis cache is the ledger.

Startup jitter and a maximum 100 records per tick remain; choose due entries by next-attempt time so a prefix of future-due entries cannot starve other due records. Use the existing 60-second loop, with immediate wake-up for new terminal intents. Apply bounded jitter and honor bounded `Retry-After`. Proposed transient schedule is 1, 2, 5, 10, 20, 40, then 60 minutes up to 24 hours. Transient delivery attempts do not consume setup repair/model/strategy budgets or relaunch setup.

Replace silent ten-attempt abandonment for v1 with durable `reconcile_pending` after the transport window: preserve bytes, alert the operator and schedule bounded reconciliation. Pending/unacknowledged data is never removed by archive retention. Budget exhaustion is a delivery condition, not proof that the business run failed. B4 may later provide the shared goal wall-clock limit; neither delivery nor reconciliation may renew that goal's budget.

Maintain at-least-once delivery. A crash after receiver commit and before acknowledgment causes the same message to be sent again. Receiver state/effect idempotency closes that ambiguity; this is not an exactly-once claim. Legacy outbox entries retain IDs and bodies through a compatibility reader; do not blindly re-drive historical failed entries or reset their event IDs.

## Receiver order, claims and acknowledgments

For v1, service authentication, body bounds, schema/ID validation and original dispatch/scope verification happen **before claim, bind, model creation or state writes**. Do not defer validation until a handler or `guarded_service_write` has already performed a binding. Unknown remote IDs may bind only through an existing backend-authorized provisional dispatch receipt and its exact scope; the worker's domain/org assertion alone cannot select a tenant.

Reuse `ContentFactoryCallbackEvent` for callback uniqueness and the existing lease concept. Validate its job/type association, and maintain reserved `delivery_v1` metadata in existing `ContentFactoryRun.result` for payload digests, execution watermarks, applied/observed dispositions and pull leases. All snapshot/result merges must preserve that namespace. An existing processed callback row without a matching digest is legacy evidence, not proof that an arbitrary v1 body is identical. A v1 collision is a typed conflict/quarantine; do not acknowledge a changed body as a duplicate.

Use existing lifecycle lock order (organization → connection → operation → run; claim association consistently within that order). Apply run/step projections, the exact receipt/digest and processed marker atomically where they share the database transaction. Compare `(generation,state_version)` within the original consent scope. Equal version with changed semantic body is a conflict; a lower version is stale. Same-version callback and snapshot may carry different event projections, but must agree on the shared state/proof digest; each callback event ID remains independently deduplicated. Ordering cannot rely on `emitted_at` wall-clock alone. A higher execution generation requires an existing authorized restart/resume receipt; it is not new consent supplied by the sender.

Terminal cancellation/denial/deletion fences win. An otherwise identical historical event can receive `200 observation_only` without reopening an operation, granting proof or running a handler. Keep stale observations separately from the authoritative latest projection. Current-scope snapshots with valid exact evidence may advance verified milestones through the **same proof validators** used by push; progress strings or worker `completed` labels alone may not. Raw observation fallback uses the existing `run_observations` stripping rules and cannot grant approval, merge, publishing readiness or deployment proof.

The existing callbacks can perform messages/refunds and other effects. Their processed stamp alone cannot make a partial external effect exactly once. For enrolled setup callbacks, extract a shared **state-only** projector and separate effect scheduling. Delivery receipts may create an idempotent effect obligation under existing JSON/operation storage, but external effects retain their existing dedupe/financial authorization requirements and are never executed by the reconciler. Audit those effect keys before enabling an event type. Do not call current `_apply_run_snapshot` and merely assume it is side-effect-free.

| Result | v1 sender disposition |
| --- | --- |
| 2xx with matching schema/kind/run/event ID/full-payload/shared-state digests and `applied`, `duplicate`, `ignored_stale`, or `observation_only` | Persist acknowledgment. A malformed/mismatched 2xx receipt is unconfirmed and retried, not success. |
| 409 `website_operation_terminal`, with authenticated structured `acknowledged=true`, matching schema/kind/run/ID/digests and original scope | Acknowledge delivery as `ack_terminal`; preserve the causal run failure. Do not call the existing producer routine that overwrites a run with a delivery rejection. |
| 409 live callback claim (`delivery_claim_pending`), capacity/lease contention or approved current retryable receiver code | Retry with backoff. A live claim is not acknowledged: the handler may still die before commit. |
| 409 cancellation/deletion/revocation/old-attempt/changed-scope code | Never rebind or replay under new consent. Retire only an exact receiver-acknowledged fenced delivery; otherwise quarantine for inspection, with no fabricated business outcome. |
| Unknown, untyped or ambiguous 409 | Preserve and retry within the delivery window; alert on repetition. No blanket “all 409 means terminal” rule. |
| 422 malformed schema/unsupported version, or same-ID changed payload | Quarantine immutable bytes and field-path/type diagnostics; alert an operator. No 500, whole-run retry, automatic schema downgrade, or customer credential-approval action. |
| 401/403, missing configuration or unsupported destination | Operator/configuration quarantine; preserve data and causal failure. Resume only after reviewed service remediation, using the same ID/body. |
| Network loss, 408, 429, 5xx | Transient delivery retry. Preserve actual HTTP status even when a provider includes a JSON message. |

Use B1's typed registry for known code/class semantics. Delivery acknowledgment/quarantine is a separate transport disposition; it must not overwrite a business failure class/fingerprint. Do not derive policy solely from HTTP status or log text. Enrolled v1 paths must return structured receipts; legacy responses use the reviewed compatibility policy and do not pretend to supply missing digests.

### B1 and goal-wide occurrence counting

Carry B1's proposed causal object unchanged: `failure={schema_version, registry_version, registry_sha256, fingerprint_version, code, failure_class, failure_fingerprint, stage, retryable, user_message, action, evidence_refs}`. Scope/run/operation/source identity belongs to the authenticated delivery envelope. A code's registered class and fingerprint do not change when recovery escalates; escalation is a separate goal recovery decision. A registry-version/digest mismatch may be decoded only by an explicitly retained historical decoder and cannot silently apply a new policy.

Deduplicate a **failure occurrence**, independently of transport `event_id`. Allocate and persist `failure_occurrence_id` once at the producer's classification/committed-state boundary; retain its original run execution, stage attempt and first classified state version across callbacks, mirror updates and pulls. A changed heartbeat/state version or new delivery ID is not another failure. A legitimately repeated stage/attempt creates a new occurrence; merely rebuilding an envelope does not. Validate provenance before associating an occurrence with the backend's saved goal, never accept a worker-supplied goal identity as authority.

B4's repeat counter is keyed by authenticated tenant, site goal, repository, connection generation, `fingerprint_version` and B1 `failure_fingerprint`, across operation attempts and strategy rungs. The occurrence receipt makes each causal observation count once; attempt and rung remain provenance, not counter-reset keys. Store the bounded seen-occurrence receipt with the existing goal/operation JSON chosen by B2/B4. If that goal identity is not yet implemented, retain delivery/occurrence receipts but do not fabricate goal-wide metrics or escalation. Implementation tests must replay one failure through callback, PUT and reconciler and observe one count, then observe two real occurrences across a rung change as two counts without altering the registered class.

## Bounded state-only reconciliation

Extend the existing scheduler, not a second unowned polling loop. Proposed defaults retain ten-minute staleness, two-minute per-run probe spacing and batch ten, with one bounded HTTP request per claimed candidate. Include known setup/scan runs whose operation receipt or delivery watermark stopped moving, including a quiet owner-action state when its child outcome is not yet accounted for. Do not continuously poll a fully acknowledged, unchanged owner-action gate.

CF adds `GET /api/runs/<id>?view=delivery_snapshot` on the existing API-key-protected route. It validates the path ID and reads only local committed STATUS plus an explicit original-scope/proof field allowlist. It performs **no formatter, recovery, preview fetch, remote fallback, mirror, callback, write or new directory creation**. Omit article HTML/code/log blobs; enforce the setup response limit. Missing, partial, corrupt or unsupported state returns typed unavailable/404/422 as appropriate, never fabricated failure/success. Authentication and approved base URL come from server configuration, never a worker-supplied URL.

The backend persists a pull lease/nonce/expiry in reserved run JSON under a short row lock and pins original scope, dispatch, generation, local version and receipt digest. Fetch outside database locks with connect/read/response-size limits. Recheck the pin and lease under lifecycle-order locks before applying; if a callback, push, reconnect or cancellation won, discard or re-evaluate the observation, never overwrite it. A fresh valid snapshot is processed through the same state-only projector, ordering and proof validation as pushed snapshots. It can repair missing state and wake the goal runner after commit; it cannot execute callback notifications, refunds, publication or merge.

The existing reconciliation sweep's recover/cancel/missing-run/refund branches remain distinct. A v1 delivery candidate must not simultaneously take those legacy inference branches. A missing snapshot alone is not proof of a missing dispatch, a failed build or a refund obligation. Active workers with unchanged state are `no_change`, not a repair. Count `delivery_reconciler_repairs_total` only when a missing valid projection/milestone is repaired; separately count unavailable probes, observations, lease conflicts and proof rejections. Any actual repair is a bug signal for delivery/coalescing, not a routine success to hide.

## Operations, retention and release

Proposed flags default off: CF `CONTENT_FACTORY_SETUP_DELIVERY_V1_ENABLED` (new enrollment) and `CONTENT_FACTORY_SETUP_DELIVERY_V1_SEND_ENABLED` (sending); backend `CONTENT_FACTORY_SETUP_DELIVERY_V1_APPLY_ENABLED` and `CONTENT_FACTORY_SETUP_DELIVERY_RECONCILIATION_ENABLED`. Add a backend shadow comparison mode that reads/validates without applying. Enrollment is a durable existing org-config/operation receipt allowlist; both endpoints retain legacy compatibility. These flag names are proposals, not existing configuration. Enrollment is sticky for an existing run execution: disabling new enrollment does not change its protocol or prevent committed v1 obligations from being spooled. Disabling send pauses only sending. With backend apply disabled, an unprocessed v1 state change returns typed retryable `503 delivery_apply_disabled`, not a successful no-op acknowledgment; a previously verified identical duplicate/fenced acknowledgment remains safe. B1's audited v0 adapter, rather than raw new aliases, handles compatible unenrolled legacy inputs.

Expose bounded counters/histograms for pending count/oldest age, durable write failures, delivery attempts/acks by typed disposition, claim contention/lease reclaim, quarantined contract errors, digest collisions, terminal fence acknowledgments, repairs and repair latency. Log event/run IDs, digest prefixes, safe scope IDs, status and field paths; never payloads, credentials, raw response bodies or tokenized URLs. A6's handler redaction remains a safety net. Pending/claimed/quarantined records are excluded from ordinary sent/failed age pruning. Keep current seven-day acknowledged and thirty-day diagnostic archives initially; retain identifier/digest replay receipts for at least the approved sender retry/archive horizon and coordinate them with existing run deletion/retention. Privacy purge wins and keeps only the existing minimal tombstones.

Rollout requires owner approval: merge Phase A and the agreed B1 contract, prove schema compatibility, persistent-volume/locking/capacity and pure GET/projector tests, deploy receivers/read mode before producers, then enable shadow and fixture-only sending. **Before any customer canary or customer-affecting delivery/policy flag, require an E4 qualifying zoo pass for its full one-shot flow through the first live article, including the B5 crash/lost-delivery/fencing faults, plus the owner's explicit release approval for the exact release.** An implementation CI pass or documentation approval is not that gate. Only then enable a small explicitly enrolled customer canary. Advance only on zero digest/proof regressions, no duplicate effects and no unexplained reconciler repairs. This note supplies no deployment authorization and does not assert a zoo night or production success.

Rollback disables new enrollment and reconciliation apply first. Preserve every unacknowledged v1 record and receipt. Existing legacy delivery continues; v1 sending can be paused without deleting its backlog. Keep the receiver schema/ack support and pure snapshot mode while v1 records remain; do not downgrade to a binary that will discard or misinterpret them. Re-enable with the same IDs/digests after remediation. Do not convert a rollback pause into a new setup attempt, owner approval or refund.

## Implementation validation after approval

Required real-chain tests replace network/database boundaries only and fail before the relevant change:

- committed transition → durable snapshot/callback intent → actual HTTP mock transport → receiver schema/lease/projector → acknowledgment; inject crash before/after producer commit, after receiver commit, and before ack persistence;
- dropped terminal callback/PUT repaired by pure GET, with one applied version and zero notifications/refunds/publication calls; repeated healthy reads count zero repairs;
- two senders/receiver claims, expired lease, stale nonce and process restart; an in-flight body stays immutable and terminal snapshots displace only safe progress;
- malformed object/list/boolean IDs, over-100 event IDs, conflicting aliases, unsupported version, legitimate dict repair diagnostics, and the legacy large `article_complete` shape; invalid v1 payload returns 422 before claim/bind/write;
- exact terminal409 acknowledgment versus live-claim/transient409 and unknown409; schema/auth quarantine preserves the original build/style failure and creates no owner credential action;
- same-ID/same-body duplicate, changed-body collision, out-of-order/equal-version conflict, valid authorized higher generation and refused invented generation;
- scope/source/commit/proof mismatch, cancelled/purged/reconnected website, missing/corrupt local status and partial artifact data; no false readiness or old-source promotion;
- pure GET instrumented to fail on any local write, mirror, remote fallback, recovery or notification; bounded reads and no new ghost directories;
- flags off/rollback preserve pending and quarantined data; archive pruning cannot delete unresolved obligations; deletion fences prevent re-creation.

Database-free tests establish control-flow contracts but not PostgreSQL transaction/lease correctness or filesystem crash durability. Implementation needs separately approved database-backed concurrency tests and a controlled volume/restart test before rollout. This documentation PR runs neither.

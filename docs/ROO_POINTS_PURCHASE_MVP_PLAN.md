# Roo Points Purchase MVP Plan

This document describes the MVP for letting members buy fixed packs of Roo Points through Roo in Slack, using Stripe-hosted payment links/invoices and crediting points only after a verified Stripe webhook confirms payment.

The purpose of this MVP is to launch cash purchase of spendable Roo Points while preserving the meaning of earned contribution points.

## Summary

Roo will understand a purchase request such as:

```text
@Roo I want to buy 10 Roo Points
```

Roo will validate the requested pack, ask for clarification if needed, request a Stripe-hosted payment link from `mlai-backend`, and reply in the same Slack thread with the link. After payment, Stripe will call a backend webhook. The backend will verify the webhook, match it to the stored purchase row, credit purchased points idempotently, and post a confirmation back to the original Slack thread.

## MVP Scope

### Included

- Slack-first purchase request handled by Roo.
- Fixed prepaid packs only.
- Stripe-hosted invoice/payment link generated by `mlai-backend`.
- Stripe webhook verification before points are credited.
- Purchased points tracked separately from earned contribution points.
- Purchased points can be spent on eligible rewards.
- Existing Roo points, rewards, coworking, task, admin, and ledger workflows continue to work.
- Confirmation posted back into the Slack thread where the purchase started.

### Not Included

- Public `/roo` frontend Checkout flow.
- Peer-to-peer transfers.
- Cash redemption.
- Bulk discounts.
- Subscriptions or recurring billing.
- Custom card forms.
- Automatic trust, status, leadership, committee eligibility, or paid-work changes from purchased points.

## Fixed Packs

Use backend-owned pack configuration for the MVP. Do not require Stripe Products or Prices yet.

| Roo Points | Price |
| --- | ---: |
| 5 | A$30 |
| 10 | A$60 |
| 25 | A$150 |
| 50 | A$300 |

Recommended backend constant:

```python
ROO_POINT_PACKS = {
    5: {"amount_cents": 3000, "currency": "aud", "label": "5 Roo Points"},
    10: {"amount_cents": 6000, "currency": "aud", "label": "10 Roo Points"},
    25: {"amount_cents": 15000, "currency": "aud", "label": "25 Roo Points"},
    50: {"amount_cents": 30000, "currency": "aud", "label": "50 Roo Points"},
}
```

Stripe Products/Prices can be introduced later if MLAI wants dashboard-managed pricing, coupons, product analytics, or public web Checkout buttons. For this MVP, backend configuration is simpler, easier to test, and keeps the pack policy in version control.

## High-Level Flow

```text
Slack user asks Roo to buy points
        |
        v
Roo parses and validates fixed pack
        |
        v
Roo calls mlai-backend purchase endpoint
        |
        v
mlai-backend creates PointsPurchase row
        |
        v
mlai-backend creates Stripe-hosted invoice/payment link
        |
        v
Roo replies with payment link in Slack thread
        |
        v
Stripe sends verified paid webhook
        |
        v
mlai-backend finds purchase by Stripe metadata / Stripe ID
        |
        v
mlai-backend credits purchased points idempotently
        |
        v
mlai-backend or Roo posts paid confirmation in original Slack thread
```

## Backend Implementation

Backend repo: `mlai-backend`

### 1. Add Purchased-Point Accounting

Current `PointsAccount` fields:

- `balance`
- `lifetime_earned`
- `lifetime_spent`

Add fields:

- `purchased_balance`
- `lifetime_purchased`

Behavior:

- Earned contribution points increase `balance` and `lifetime_earned`.
- Purchased points increase `balance`, `purchased_balance`, and `lifetime_purchased`.
- Purchased points must not increase `lifetime_earned`.
- Spending points should continue to decrease spendable `balance`.

Recommended ledger addition:

- Add `purchase` as a ledger source type.

Optional but cleaner long-term:

- Add `Ledger.point_type` with values like `earned`, `purchased`, `mixed`.

For the MVP, `source='purchase'` plus the new account fields is enough if reward eligibility does not need to distinguish exactly which point type was spent.

### 2. Add Purchase Model

Add a model called `PointsPurchase`.

Suggested fields:

```text
id: UUID primary key
user: FK to core.User
slack_user_id: string
points: int
amount_cents: int
currency: string, default "aud"
status: pending | paid | failed | expired
stripe_invoice_id: nullable unique string
stripe_payment_intent_id: nullable string
stripe_checkout_session_id: nullable string, optional future compatibility
payment_url: URL/text
purchase_from: JSON object
ledger_entry: nullable FK to Ledger
metadata: JSON
created_at
updated_at
paid_at
```

`purchase_from` stores origin-specific details. For the MVP, purchases originate from Slack through Roo:

```json
{
  "source": "slack",
  "slack_user_id": "U123",
  "slack_channel_id": "C123",
  "slack_thread_ts": "1712345678.000100"
}
```

This keeps the model flexible for future purchase origins such as the public `/roo` page, admin-created purchases, or other community surfaces.

Important constraints:

- `stripe_invoice_id` should be unique when present.
- `ledger_entry` should only be set once.
- `status='paid'` should be terminal for successful purchases.

### 3. Add Purchase Creation Service

Add a service called `PointsPurchaseService`:

```python
PointsPurchaseService.create_purchase(
    slack_user_id: str,
    points: int,
    purchase_from: dict | None = None,
) -> PointsPurchase
```

Responsibilities:

- Validate `points` is one of `5`, `10`, `25`, or `50`.
- Resolve or create the local user for the Slack ID.
- Create a local `PointsPurchase(status='pending')` row before contacting Stripe.
- Store Slack origin details in `purchase_from`.
- Create the Stripe-hosted invoice/payment link.
- Include local purchase identity in Stripe metadata.
- Save Stripe IDs and payment URL back to the purchase row.

Stripe metadata should include:

```python
metadata={
    "points_purchase_id": str(purchase.id),
    "slack_user_id": slack_user_id,
    "points": str(points),
}
```

### 4. Add Purchased Credit Service

Add a method separate from normal contribution awarding:

```python
PointsService.credit_purchase(
    user: User,
    points: int,
    purchase: PointsPurchase,
    stripe_invoice_id: str,
) -> tuple[Ledger, bool]
```

Responsibilities:

- Use a stable idempotency key, for example:

```python
idempotency_key = f"points_purchase:{purchase.id}:paid"
```

- Create a `Ledger` row with:
  - positive `delta`
  - `kind='EARN'` or a new kind if introduced
  - `source='purchase'`
  - `reference_type='ROO_POINTS_PURCHASE'`
  - `reference_id=str(purchase.id)`
- Increase:
  - `PointsAccount.balance`
  - `PointsAccount.purchased_balance`
  - `PointsAccount.lifetime_purchased`
- Do not increase:
  - `PointsAccount.lifetime_earned`

This method should be transaction-safe and safe to call repeatedly.

The ledger row is appended only after a verified successful Stripe payment event. Creating a pending purchase must not create or reserve ledger entries.

### 5. Add Backend API for Roo

Add an endpoint under the existing points API, for example:

```text
POST /api/v1/points/purchases/
```

Request:

```json
{
  "slack_user_id": "U123",
  "points": 10,
  "purchase_from": {
    "source": "slack",
    "slack_channel_id": "C123",
    "slack_thread_ts": "1712345678.000100"
  }
}
```

Response:

```json
{
  "id": "purchase-uuid",
  "status": "pending",
  "points": 10,
  "amount_cents": 6000,
  "currency": "aud",
  "payment_url": "https://..."
}
```

Permissions:

- Use Roo/internal API key permissions, consistent with other Roo points endpoints.

Validation:

- Missing Slack user ID returns 400.
- Missing points returns 400.
- Unsupported pack returns 400 with allowed packs.

### 6. Add Stripe Webhook Endpoint

Add a webhook endpoint such as:

```text
POST /api/v1/points/stripe/webhook/
```

Responsibilities:

- Verify `Stripe-Signature` using `STRIPE_WEBHOOK_SECRET`.
- Handle the event for paid invoices/payment confirmation.
- Read `points_purchase_id` from Stripe metadata.
- Fallback to `stripe_invoice_id` lookup if metadata is missing.
- Lock the purchase row with `select_for_update()`.
- If already paid and ledger entry exists, return success without double-crediting.
- Credit purchased points using `PointsService.credit_purchase(...)`.
- Mark purchase as `paid`, set `paid_at`, save Stripe payment IDs.
- Trigger Slack thread confirmation.

### 7. Configure Stripe Webhook Delivery

Webhook setup is an explicit part of the MVP. It should be designed early, tested before launch, and configured manually in Stripe for the first release.

Recommended setup approach:

- Local development: use Stripe CLI webhook forwarding.
- Test/staging: manually create a test-mode webhook endpoint in the Stripe Dashboard.
- Production: manually create a live-mode webhook endpoint in the Stripe Dashboard after the production URL is confirmed.
- Automation: defer API-created webhook endpoints until after MVP unless there is a strong deployment need.

Why manual first:

- Stripe's Dashboard is the common path for registering and testing webhook endpoints.
- Manual setup makes it obvious which mode is active: test or live.
- The webhook signing secret is generated per endpoint and must be copied into the matching environment.
- API-created webhook endpoints are possible, but they add secret-management and environment-bootstrap complexity that is not needed for this MVP.

Webhook endpoint URL:

```text
https://api.mlai.au/api/v1/points/stripe/webhook/
```

Local development URL when using Stripe CLI forwarding:

```text
http://localhost:8000/api/v1/points/stripe/webhook/
```

Enabled events:

```text
invoice.paid
invoice.payment_failed
```

If the implementation uses Checkout Sessions instead of invoices later, add:

```text
checkout.session.completed
```

For the agreed invoice/payment-link MVP, `invoice.paid` is the event that credits points.

Recommended sequence:

1. Add the backend webhook view with signature verification.
2. Add tests that mock Stripe webhook construction and paid events.
3. Test locally with the Stripe CLI forwarding events to the local backend.
4. Manually configure a test-mode webhook endpoint in the Stripe Dashboard for staging/test deployment.
5. Copy that endpoint's signing secret into the test/staging environment as `STRIPE_WEBHOOK_SECRET`.
6. Verify a real test-mode purchase credits points exactly once.
7. Manually configure the live-mode webhook endpoint in the Stripe Dashboard.
8. Copy the live endpoint's signing secret into production as `STRIPE_WEBHOOK_SECRET`.
9. Run one controlled live-mode smoke test.

Do not rely on Roo polling for payment completion. Stripe webhook delivery is the system of record for paid confirmation.

Environment variables needed:

```text
STRIPE_SECRET_KEY=sk_test_...
STRIPE_WEBHOOK_SECRET=whsec_...
```

Production setup should happen after the endpoint exists, has tests, and the exact public URL is known. Until then, local and test-mode webhook forwarding is enough for development.

### 8. Slack Confirmation After Payment

Store Slack routing fields on `PointsPurchase.purchase_from`:

- `source`
- `slack_channel_id`
- `slack_thread_ts`

When the webhook marks the purchase paid, post:

```text
Payment received. Credited 10 purchased Roo Points to <@U123>.
```

Preferred long-term option:

- Backend tells Roo via an internal endpoint/callback, and Roo posts the Slack message.

Fastest MVP option:

- Backend posts directly to Slack using the bot token if the backend already has the required Slack configuration.

Either option is acceptable for MVP as long as the purchase row stores the Slack channel and thread timestamp.

## Webhook Matching Strategy

Use local database identity as the primary source of truth.

1. Backend creates `PointsPurchase` before creating the Stripe object.
2. Backend passes `purchase.id` in Stripe metadata.
3. Stripe webhook includes that metadata.
4. Backend loads the purchase row by ID.
5. Backend credits points using a ledger idempotency key.

Primary lookup:

```python
purchase_id = stripe_object.metadata["points_purchase_id"]
purchase = PointsPurchase.objects.select_for_update().get(id=purchase_id)
```

Fallback lookup:

```python
purchase = PointsPurchase.objects.select_for_update().get(
    stripe_invoice_id=stripe_object.id
)
```

This avoids guessing from amount, email, or Slack user ID.

## Idempotency Rules

Stripe may deliver webhooks more than once. Duplicate webhook delivery must not double-credit points.

Use all of the following:

- Unique `stripe_invoice_id` on `PointsPurchase`.
- Stable `Ledger.idempotency_key`.
- Transaction around purchase update and ledger credit.
- If purchase is already `paid` and has `ledger_entry`, return 200.

Example idempotency key:

```python
points_purchase:{purchase.id}:paid
```

## Open Decisions

### Should We Use Stripe Products/Prices?

Recommendation for MVP: no. Use dynamic invoice/payment line items with backend-owned pack config.

Revisit if the frontend `/roo` page launches public Checkout buttons or if pricing should be managed by non-engineers in the Stripe dashboard.

### Who Posts The Paid Slack Confirmation?

Recommendation for MVP: choose the fastest reliable path.

Option A: backend posts directly to Slack.

- Faster if backend has Slack token/config.
- Slightly mixes payment and Slack behavior.

Option B: backend calls Roo and Roo posts to Slack.

- Cleaner service boundary.
- More moving parts.

Either way, store Slack channel/thread on `PointsPurchase.purchase_from`.

### Do Purchased Points Need Spend Ordering?

For MVP, purchased points can be spendable from the same `balance`.

If MLAI later needs detailed controls such as “spend purchased points before earned points” or reward-specific eligibility, add explicit spend allocation:

- `earned_balance`
- `purchased_balance`
- spend ledger allocation metadata.

For this MVP, the core invariant is simpler:

```text
purchased points are spendable but do not count as earned contribution.
```

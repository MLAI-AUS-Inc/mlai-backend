# P2 founder notifications and journey

`MY_STARTUP_TRANSITION_NOTIFICATIONS_ENABLED` owns transitions only for the current P2 cohort. `MY_STARTUP_TURN_REMINDERS_ENABLED` additionally permits the 24-hour and 72-hour reminders. All provider delivery remains outside database transactions. The old goal notifier stands down for these organizations; other organizations retain its previous path. The P1 draft-ready notifier keeps its copy and key, gains actual pre-preview readiness, and rechecks the current requester/membership and verified email while the P2 recipient gates are active.

`founder_transitions` reserves one callback ledger row per item, event, recipient and channel under an organization lock. Its private `founder_notices.last` records state, ask, transition event and entry time. Private outbox metadata freezes the logical identity, message, destination and actual signed DM event or email payload before sending. A claim compare-and-set excludes concurrent drains; lost acknowledgements replay the same identity. Recipient removal, owner changes, publish-right changes, revoked devices, changed email addresses and a completed ask are checked again before the final send. Owner-only asks are independently filtered even if an optional provider returns a broad list. No CC/BCC or cross-member email field is produced.

The exact logical key is `founder-transition:<org>:<item>:<event>:<ask-or-state>:<recipient>:<email-or-dm>`. The existing callback ledger has a 100-character column: keys that fit are stored verbatim; overflow uses a deterministic `founder-transition:<sha256>` representation while retaining the full logical key privately. The provider receives the full key when it fits its [256-character limit](https://resend.com/changelog/idempotency-keys); only provider overflow uses the same deterministic representation. Retries stop before its 24-hour retention window (23 hours from reservation). No migration is introduced.

The sweep observes bounded current article/website items and current pending team request UUIDs. A round-robin scan cursor prevents later organizations from starving. Dormant organizations without work are excluded in SQL. Website goal proofs and current verified setup state can produce `blog_live`; copy-ready delivery cannot produce `article_live`. Reviewed publication follows only the backend's same-organization source/approved-body-bound child seam. An existing bound child can show Publishing or its attested live URL while the original article ID and billing identity stay intact.

The P2 projection adds current claim counts, actual points outcomes, safe developer handoffs, optional publish offers and team fields. Pending channel intent or an applied conversion cannot declare copy delivery; the CF completed acknowledgement and real export evidence are required. Unknown failures remain Working on it. The copy ID replaces `holdingReason`. A pending or retained charge uses truthful text instead of claiming No charge. A member's owner-only ask retains its state/line with `viewerRole:member` for the existing client substitution. `website.connectedBy.firstName` is emitted only with the team flag and a real current config-bound connected website; email and full-name fallbacks are excluded. Staff console signaling is independent of cohort, as specified.

Production sends, deployment, token minting, real broker deliveries and canaries were not run. The synthetic PostgreSQL suite verifies current team composition, actual concurrent claims, reminders, frozen email/DM replay, current-recipient checks, every projection precedence rule, preserved legacy payloads and bounded sweeps. Release validation must inspect notifier credentials and dedicated Chat signer/relay configuration before enabling notification flags.

## Approved staff reservation integration

The real UTF8 500-active-item full tick initially exceeded two seconds because staff incident reservation performed per-item reads, locks and writes. The orchestrator approved `staff_alert_rules.py` plus a narrow batch helper in `founder_journey_alerts.py`. The batch still evaluates and reserves every incident with the same stable IDs, sanitized details, business-day acknowledgement deadline, existing index dedupe and orphan mirror adoption. It locks and merges configuration rows in a batch, releases those locks, then reloads and locks fresh run rows before mirroring only `result.ops_alerts`. This preserves a concurrent CF callback's status, timestamp and other result fields. Existing alert delivery and its provider claim protocol remain in charge. Actual PostgreSQL tests compare single/batch receipts, prove concurrent replay/callback races, and bound 500 reservations to at most 16 queries; the full all-runners tick is measured with the same active workload and strict two-second assertion.

# P2 founder notifications and journey

`MY_STARTUP_TRANSITION_NOTIFICATIONS_ENABLED` owns transitions for every cohort (plan E7; it once covered only the P2 cohort). `MY_STARTUP_TURN_REMINDERS_ENABLED` additionally permits the 24-hour and 72-hour reminders. All provider delivery remains outside database transactions. The old goal notifier stands down for these organizations; other organizations retain its previous path. The P1 draft-ready notifier keeps its copy and key, gains actual pre-preview readiness, and rechecks the current requester/membership and verified email while the P2 recipient gates are active.

`founder_transitions` reserves one callback ledger row per item, event, recipient and channel under an organization lock. Its private `founder_notices.last` records state, ask, transition event and entry time. Private outbox metadata freezes the logical identity, message, destination and actual signed DM event or email payload before sending. A claim compare-and-set excludes concurrent drains; lost acknowledgements replay the same identity. Recipient removal, owner changes, publish-right changes, revoked devices, changed email addresses and a completed ask are checked again before the final send. Owner-only asks are independently filtered even if an optional provider returns a broad list. No CC/BCC or cross-member email field is produced.

The exact logical key is `founder-transition:<org>:<item>:<event>:<ask-or-state>:<recipient>:<email-or-dm>`. The existing callback ledger has a 100-character column: keys that fit are stored verbatim; overflow uses a deterministic `founder-transition:<sha256>` representation while retaining the full logical key privately. The provider receives the full key when it fits its [256-character limit](https://resend.com/changelog/idempotency-keys); only provider overflow uses the same deterministic representation. Retries stop before its 24-hour retention window (23 hours from reservation). No migration is introduced.

The sweep observes bounded current article/website items and current pending team request UUIDs. A round-robin scan cursor prevents later organizations from starving. Dormant organizations without work are excluded in SQL. Website goal proofs and current verified setup state can produce `blog_live`; copy-ready delivery cannot produce `article_live`. Reviewed publication follows only the backend's same-organization source/approved-body-bound child seam. An existing bound child can show Publishing or its attested live URL while the original article ID and billing identity stay intact.

The P2 projection adds current claim counts, actual points outcomes, safe developer handoffs, optional publish offers and team fields. Pending channel intent or an applied conversion cannot declare copy delivery; the CF completed acknowledgement and real export evidence are required. Unknown failures remain Working on it. The copy ID replaces `holdingReason`. A pending or retained charge uses truthful text instead of claiming No charge. An article whose saved request charged nothing (neither paid nor a free first article) reads No charge while its points receipt is pending; a publication child keeps its own outcome. A run the owner or a website action stopped (the owner's cancel, Clear saved setup, disconnect, reconnect, revoke, purge, or a cancelled website operation) gets no P2 line, and neither does a stopped setup run from an older connection generation or one Clear saved setup tombstoned. A setup stop that is ours to fix shows the setup copy with no article points line and the `setup` stage. A member's owner-only ask retains its state/line with `viewerRole:member` for the existing client substitution. `website.connectedBy.firstName` is emitted only with the team flag and a real current config-bound connected website; email and full-name fallbacks are excluded. Staff console signaling is independent of cohort, as specified.

Production sends, deployment, token minting, real broker deliveries and canaries were not run. The synthetic PostgreSQL suite verifies current team composition, actual concurrent claims, reminders, frozen email/DM replay, current-recipient checks, every projection precedence rule, preserved legacy payloads and bounded sweeps. Release validation must inspect notifier credentials and dedicated Chat signer/relay configuration before enabling notification flags.

## Approved staff reservation integration

The real UTF8 500-active-item full tick initially exceeded two seconds because staff incident reservation performed per-item reads, locks and writes. The orchestrator approved `staff_alert_rules.py` plus a narrow batch helper in `founder_journey_alerts.py`. The batch still evaluates and reserves every incident with the same stable IDs, sanitized details, business-day acknowledgement deadline, existing index dedupe and orphan mirror adoption. It locks and merges configuration rows in a batch, releases those locks, then reloads and locks fresh run rows before mirroring only `result.ops_alerts`. This preserves a concurrent CF callback's status, timestamp and other result fields. Existing alert delivery and its provider claim protocol remain in charge. Actual PostgreSQL tests compare single/batch receipts, prove concurrent replay/callback races, and bound 500 reservations to at most 16 queries; the full all-runners tick is measured with the same active workload and strict two-second assertion.

## Every cohort, per-action staff thresholds and the owner wait (plan E7, E13)

`MY_STARTUP_TRANSITION_NOTIFICATIONS_ENABLED` now owns transitions for every cohort, legacy included (decisions D14 and D15). The goal notifier therefore stands down for legacy startups as well; its needs-you and done notices are covered by the ladder's `website:` item (same operation notice, same canonical asks). Both flags still default off and are switched by repo variables (step A15), never by code. The first-run cap (`FIRST_RUN_SEND_CAP` per sweep) and the one-follow-up rule for backlog asks (A22) apply unchanged to the legacy cohort.

Rungs are 0, 24 and 72 hours. Each rung is reserved once in the callback ledger and the private outbox and re-projected before each send, so it stops when the ask clears, and a redeploy or a fresh process (empty cache, new cursor) never sends a rung twice.

While `ARTICLES_FOUNDER_JOURNEY_ALERTS_ENABLED` is also on, an ask that waits past its threshold queues one `ask_waiting` staff alert (72 hours by default; 120 hours for `approve_on_github`, `approve_setup` and `authorize_github`, where a slow review, merge or permission is normal; 72 hours for the owner wait). The alert id is stable per item, ask and ask start. When the ask clears or changes, the alert gets `resolved_at`; a still-pending alert becomes `resolved` and is never delivered. For an item the ladder follows, the generic `your_turn_72h` detector stands aside so staff do not get two alerts: only while the ladder last saw the item as a founder ask and has either raised its own alert or is still inside that ask's threshold plus 12 hours. An item the ladder stopped following (outside its latest-20-runs window, behind a newer setup run, or recorded as no longer the founder's turn) falls back to the generic detector, so a stuck founder always reaches staff.

The founder's GitHub organisation-owner request (`article_system.github_owner_request`) is its own item, `github-owner:<org>`, sent only to the founder who asked. `waiting_github_owner_approval` carries the copyable owner link (the app's public installation page, no state or identity); if the owner's approval arrives but no single repository matches, or the request is older than 30 days, the ask becomes `choose_repository`, which opens the repository picker. The developer path is the existing team invite (invite link or email invitation); a developer acts under their own login, and no login-free delegate link exists.

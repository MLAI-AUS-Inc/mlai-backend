# Publishing-input candidates: receiver foundation

An old native contract digest does not cover all listing, runtime and publishing inputs. A fresh checksum of today's inputs also does not prove that a verifier executed them. This receiver keeps those two facts separate.

The pinned CF schema and actual generated React/static candidates use compact sorted UTF-8 JSON, with no coercion, implicit defaults, unknown fields, credentials or open metadata dictionaries. The initial profile supports the existing React registry and static shared-JSON publishers. Rich target configuration, private build environments, hooks and preview-discovery extensions remain unsupported in this candidate profile. Existing legacy integrations retain their current protocol and historical proof.

The sole candidate location is `target.contract.publishing_inputs_v1`. Its full frozen publishing target must agree with the surrounding target. Scans may store a valid candidate as an unverified proposal. They cannot promote it using copied legacy `verified` flags, and same-source scans still preserve an already accepted target under #1141. Once a target carries a candidate, scan/config writes cannot remove it and restore legacy readiness, even while it is pending or after the source changes. The selected pending target also survives a worker's replacement-default proposal. A candidate does not become an accepted certificate by being serialized or hashed.

Until the next paired protocol increment is ready, candidate-bearing targets are explicitly refused by legacy provider promotion, both before and after the provider read. Saved-receipt access, current-proof reuse, automatic source-proof discovery and live-deployment verification also refuse them. Self-reported schema3/input-digest fields cannot bypass that boundary. No flag enables schema3 acceptance in this change.

Next increment, required before enabling CF candidate generation: make native and hosted executors check exactly the frozen inputs they are about to consume; seal schema3 provider evidence with the input digest; bind candidate source, operation, runtime and verifier identities; promote an explicitly pending candidate atomically while retaining the previous accepted target during migration. Then carry accepted input identity through live, journey, goal, queue and actual publisher readers. Legacy proof must never be upgraded merely by hashing configuration. No new paid article in the enrolled migration cohort may start before its exact-source proof.

Validation uses the actual CF fixtures, adversarial shape/mapping/path cases and the real scan/promotion/live readers with only persistence/provider boundaries substituted. The normal strict runner denies SQL and network. CI additionally checks schema/fixture bytes against the immutable private CF source using the existing read-only secret. All rollout flags remain off. This is a prerequisite, not completion of R0 full-input assurance or any live gate.

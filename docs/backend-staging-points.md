# Backend staging contracts

Staging composes the normal `mlai.urls` tree after small environment-specific auth/member adapters. Default-auth domain endpoints accept the independent staging account session; service/admin/org checks remain domain-owned. No production JWT or local developer JWT is accepted by the hosted profile.

See [developer quickstart](backend-staging-development.md) for login, local setup and normal-function deployment. See [meeting-room booking](meeting-room-booking.md) for the real room service's limits. Eight marked synthetic users and DB-only examples do not imply external integrations are available.

## Synthetic fixtures and member adapters

Private provisioning manifest contains exactly `ashwin@staging.mlai.au`, `volunteer01@staging.mlai.au` through `volunteer07@staging.mlai.au`, independent password files and display names. Preview then `provision_staging_pilot --manifest <private-file> --preserve-existing --apply`; preview then `seed_staging_points --manifest <private-file> --apply`. Commands require the exact isolated hosted profile/database, never email or reset an existing account, and fail on unmarked/privileged/unmarked or privileged conflicting identities; existing marked account passwords remain unchanged, including tester-initiated password changes. Seed replay preserves data, spending, stock and existing pilot credentials. Each new account starts with12 general Roo +24 digital Roo, a linked synthetic contribution and synthetic small/big rooms.

Member adapters in staging preserve the normal room DTO/service and derive the account from the session. GET `/api/v1/points/meeting-rooms/rooms/`; POST availability with room_slug, starts_at, ends_at and UUID client_request_id; POST book with those exact fields plus returned signed preview. Preview is bound to user/session/interval/cost/request and expires after ten minutes. Keep the request UUID/preview for an uncertain retry. A committed matching retry returns the existing booking even after expiry; changed payload is a conflict. POST my-bookings with `{}` and cancel with booking_id. One/two hours cost1/2 general Roo, maximum4hr/day,30days ahead; no digital spend, other-owner cancellation or cancellation after start. No real calendar/Slack/venue action occurs.

GET `/api/v1/points/me/ledger/` returns own history. GET/POST `/api/v1/points/me/rewards/` supports synthetic reward_code, positive quantity, UUID client_request_id; exact retries preserve stock/debit. STAGING_MANUAL remains pending without an operator fulfillment worker. POST `/api/v1/points/me/purchases/` takes pack_id, UUID client_request_id, consent:true; returns a real synthetic pending purchase, never a production checkout link. POST `/api/v1/points/me/purchases/outcome/` with purchase_id and outcome paid/cancelled/failed resolves owned local records once. This is a clearly labelled payment simulation; paid credits the real purchased bucket without pretending a payment charge or receipt exists. Production never registers these adapters. External providers and unsupported workers remain unavailable.
